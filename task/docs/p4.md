# P4. Развёртывание на Helios с контролем качества доставки

## Общая схема

В проекте используется один workflow для Helios: `.github/workflows/p4-helios.yml`. Он выполняет и обычную публикацию `main`, и preview-публикацию веток. В нём же находятся healthcheck, резервирование предыдущего релиза и rollback.

Общий путь P4 выглядит так:

```text
push в preview-ветку
        |
        v
resolve_target
определение branch slug, URL и удалённого каталога
        |
        v
build-and-deploy
checkout -> установка зависимостей -> mkdocs build --strict
        |
        v
архив site/ -> SCP на Helios -> staging-каталог
        |
        v
backup предыдущей версии -> замена target-каталога
        |
        v
healthcheck опубликованного URL
```

P4 workflow запускается автоматически после push в любую ветку, включая `main`. Для `main` используется корневой production-каталог, для остальных веток — отдельные preview-каталоги.

При ручном запуске есть параметр `rollback`. При значении `false` выполняются сборка и деплой. При значении `true` сборка пропускается и запускается отдельная job отката.

## Подготовка и выбор каталога

Первой запускается job `resolve_target`. Она получает имя ветки из `github.ref_name` и приводит его к безопасному имени каталога: символы `/` и `_` заменяются на `-`, остальные недопустимые символы удаляются.

Для `main` используются:

```text
URL:    https://se.ifmo.ru/~s506308/project-python/
каталог: ~/public_html/project-python
```

Для ветки `demo-p4` используются:

```text
URL:    https://se.ifmo.ru/~s506308/project-python/previews/demo-p4/
каталог: ~/public_html/project-python/previews/demo-p4
```

Эти три значения job передаёт следующим job через outputs: `branch_slug`, `site_url` и `remote_dir`. Благодаря этому остальной workflow не содержит отдельных копий логики для production и preview.

## Сборка и передача сайта

В job `build-and-deploy` сначала выполняются стандартные шаги:

1. GitHub Actions забирает выбранный commit через `actions/checkout`.
2. Устанавливается Python 3.13 и зависимости из `requirements.txt`.
3. MkDocs собирает сайт командой `python -m mkdocs build --strict`.
4. Переменная `SITE_URL` получает адрес именно выбранной ветки. Поэтому ссылки на сайте формируются с правильным подкаталогом preview.
5. Каталог `site/` упаковывается в tar-архив.
6. Архив сохраняется как GitHub Actions artifact для отладки.
7. `appleboy/scp-action` передаёт архив на Helios через SSH-порт 2222.

Для подключения используется deploy-ключ `HELIOS_SSH_KEY` из GitHub Secrets. Сам ключ в репозитории не хранится.

## Публикация на сервере

После SCP запускается `appleboy/ssh-action`. На сервере создаются три понятия:

```text
 target:       публичный каталог текущей версии
 staging:      временный каталог конкретного релиза
 backup_root:  место хранения предыдущей версии
```

Например, для `demo-p4` это выглядит так:

```text
~/public_html/project-python/previews/demo-p4
~/.helios-staging/<run-id>-<sha>
~/.helios-backups/project-python/demo-p4
```

Архив сначала распаковывается в staging. Публичный каталог до этого момента не меняется. Затем прежний target переносится в:

```text
~/.helios-backups/project-python/<branch>/previous
```

и staging переименовывается в target. Таким образом, опубликованный каталог заменяется целиком, а не обновляется отдельными файлами. Это уменьшает вероятность смешать файлы старой и новой версии.

В shell-скрипте установлен `trap` на ошибку. Если после удаления target новая версия не успела занять его место, скрипт возвращает `previous` обратно в публичный каталог.

## Healthcheck после развёртывания

Healthcheck выполняется последним шагом обычного `build-and-deploy`, то есть уже после передачи архива и замены публичного каталога.

Фактически workflow делает следующее:

```bash
response="$(curl --fail --silent --show-error \
  --location --retry 3 --max-time 30 "$HEALTHCHECK_URL")"
grep -Fq "Исследовательские материалы" <<< "$response"
```

Проверка состоит из двух частей.

### Проверка HTTP-ответа

`curl --fail` считает запрос неуспешным, если сервер вернул ошибку 4xx или 5xx. Параметр `--location` разрешает переходы, если Helios отвечает редиректом. `--retry 3` даёт серверу несколько попыток, а `--max-time 30` не позволяет job зависнуть надолго.

При успешном ответе HTML сохраняется в переменную `response`. Если сайт недоступен, URL неправильный или Helios возвращает ошибку, команда `curl` завершается с ненулевым кодом. Из-за `set -euo pipefail` весь шаг и job становятся красными.

### Проверка контрольной строки

Затем `grep -Fq` ищет в полученном HTML строку:

```text
Исследовательские материалы
```

Это простая проверка того, что по адресу находится именно наш сайт, а не чужая страница, пустой каталог или страница ошибки с кодом 200. Если строка не найдена, `grep` возвращает ошибку, поэтому workflow также завершается с ошибкой.

## Preview-сборки

Preview нужен, чтобы проверить изменения ветки до публикации в production.

Например, создаётся ветка:

```bash
git switch -c demo-p4
git push -u origin demo-p4
```

После push автоматически запускается P4 workflow. Ветка `demo-p4` публикуется в:

```text
https://se.ifmo.ru/~s506308/project-python/previews/demo-p4/
```

Ветка `feature/results` будет преобразована в каталог:

```text
~/public_html/project-python/previews/feature-results
```

Каждая ветка получает свой каталог и свой `SITE_URL`, поэтому preview одной ветки не перезаписывает preview другой ветки и production-сайт.

Для `main` используется корневой каталог без `previews`. В текущей конфигурации push в `main` также обрабатывает `p4-helios.yml`, поэтому production получает те же backup, healthcheck и поведение при ошибках, что и preview.

## Откат предыдущей версии

При каждом успешном P4-деплое предыдущая версия сохраняется до установки новой. Для каждой ветки backup отдельный:

```text
main:
~/.helios-backups/project-python/main/previous

demo-p4:
~/.helios-backups/project-python/demo-p4/previous
```

Чтобы выполнить rollback для preview:

1. открыть **Actions**;
2. выбрать **P4 quality deployment to Helios**;
3. нажать **Run workflow**;
4. выбрать ветку `demo-p4`;
5. установить `rollback: true`;
6. запустить workflow.

Для production выбирается ветка `main`.

При rollback job снова вычисляет target и backup по выбранной ветке. Затем выполняется обмен каталогов:

```text
текущий target       -> rollback-current
previous             -> target
rollback-current     -> previous
```

После этого запускается такой же healthcheck. Он проверяет уже восстановленную версию. Rollback невозможен до первого успешного P4-деплоя выбранной ветки, потому что до этого ещё нет каталога `previous`.

## Поведение при обрыве развёртывания

Если соединение оборвалось на этапе SCP, архив не попал на сервер полностью, но публичный каталог ещё не трогался. Старая версия продолжает работать.

Если архив передан, но ошибка произошла во время распаковки в staging, публичный каталог также остаётся прежним.

Если ошибка произошла после переноса старого target в backup, shell `trap` пытается вернуть его обратно. В этом случае workflow завершится ошибкой, но предыдущая версия должна снова стать доступной.

Остаётся небольшой риск внезапного отключения самого сервера в момент между двумя операциями `mv`. Это не транзакция файловой системы, поэтому в таком редком случае может потребоваться ручное восстановление из:

```text
~/.helios-backups/project-python/<branch>/previous
```

После любого неуспешного деплоя результат проверяется healthcheck-ом или обычным запросом `curl`.

## Сравнение GitHub Pages и Helios

Оба варианта начинают с одной и той же операции: GitHub Actions забирает commit, устанавливает зависимости и собирает статический каталог `site/`. Дальше пути расходятся.

GitHub Pages использует официальный механизм GitHub: собранный каталог загружается как Pages artifact, а затем передаётся в `deploy-pages`. Это удобно, потому что весь процесс виден в интерфейсе GitHub, а deployment получает собственный статус и URL. При отладке ожно открыть конкретный job, посмотреть лог сборки и отдельно лог deploy.

Helios работает более непосредственно. После сборки архив передаётся на сервер по SSH, а затем удалённая команда распаковывает его и меняет каталоги. Иожно самостоятельно делать preview-каталоги, хранить backup и запускать rollback. Дополнительные критичные места такого подхода - SSH-ключ, свободное место на сервере, права доступа, правильность удалённого пути и доступность Helios.

По времени доставки нельзя честно назвать постоянного победителя. GitHub Pages обычно добавляет загрузку artifact и отдельный deployment-шаг. Helios добавляет SCP, SSH-команду и healthcheck. На небольшом сайте разница чаще всего измеряется секундами и зависит от кэша pip, нагрузки GitHub runner и скорости соединения с Helios.

По надёжности GitHub Pages выигрывает готовой инфраструктурой deployment. Helios в этой работе компенсирует зависимость от SSH резервной копией, staging-каталогом и healthcheck-ом. То есть Helios не становится таким же управляемым сервисом автоматически, надежность достигается дополнительными шагами workflow.

По удобству отладки GitHub Pages проще для стандартного сценария публикации. У Helios отладка проблематичнее, т.к. кроме лога GitHub Actions иногда приходится проверять удаленные каталоги и состояние предыдущего backup. Зато при проблеме с конкретной веткой легче понять, где она опубликована, потому что путь preview однозначно соответствует branch slug.


## Дополнения

- `HELIOS_SSH_KEY` хранится только в GitHub Secrets;
- пароль Helios не используется в workflow;
- healthcheck проверяет HTTP и одну контрольную строку, но не все ссылки сайта;
- backup занимает место на Helios;
- preview-каталог удалённой ветки не удаляется автоматически после удаления ветки Git;
- rollback можно выполнять только для ветки, у которой уже есть успешный P4-релиз.

## Вывод по Workflow

Workflow для Helios сначала определяет, куда должна попасть выбранная ветка, затем собирает и архивирует сайт, передаёт его по SSH, сохраняет предыдущую версию, публикует новый каталог и проверяет результат реальным HTTP-запросом. Благодаря этому отдельно проверяются не только успешность сборки, но и факт доступности именно опубликованной версии.
